### Placement support is different from persistence and framing

For ordinary rope, `WorldGen.PlaceTile` falls through to generic tile creation: it has no player-adjacency requirement. An isolated rope created through it is therefore **not** evidence that a player could place rope there. R1.

The ordinary item branch accepts a cardinal neighbor whose tile is present and is solid, a beam, a rope, or minecart track; a wall in a cardinal neighbor or the target also qualifies. A diagonal-only block does not qualify. This branch tests presence/type flags, not slope/half-block geometry, and uses `active()` rather than `nactive()`; do not assume an actuated neighbor must fail adjacency. Ordinary rope is absent from `CanPlaceNextToNonSolidTile`'s special set. Thus a Maw full solid can supply adjacency just as a vanilla solid does; nearby unsafe Maw walls can accidentally make a supposed unsupported negative control valid. R2, R5.

Framing separately treats solid neighbors as visual connections: above excludes solid-top tiles; below accepts solid types; sides connect when the top is not already connected. Earlier frame normalization accounts for slope-facing edges and half blocks. Start with full, unactuated supports; compare slope/half-block variants against matched vanilla geometry instead of inventing new support rules. The rope framing branch does not enforce a persistent load-bearing anchor or kill an unsupported chain. **Expected from R1:** removing its original support leaves remaining ordinary rope, with reframing; verify this in the future run rather than expecting a vine-style cascade.

`WorldGen.IsRope` recognizes a present rope tile. It also recognizes a platform or track cell sandwiched vertically between present rope tiles. It does not turn an arbitrary solid Maw block into a climb-through rope segment. Item placement onto existing rope can redirect the target down the contiguous rope/platform/track run toward an empty cell, with world-bottom/lava checks. Keep this automatic-extension case separate and preflight its whole scan path; a small nominal target rectangle alone does not bound it. R2, R3.

### Player attachment and ascent constraints

`FindPulley()` requires Up or Down and no active portable stool. It samples `x = (int)(position.X + width/2)/16`, `y = (int)(position.Y - 8)/16`: rope must reach the head/grab region, not merely the feet. It tries centered/side positions with native solid-collision checks; Terraria itself may align X and zero horizontal velocity. R3.

The normal update only attempts attachment without Jump, mounting, grappling, inverted gravity, rope cooldown, frozen/webbed/stoned state or tongued state. While attached, Up needs rope above the sampled position and collision clearance; native acceleration starts at `-0.2` pixels/update², slows to `-0.02` beyond upward speed 3, and caps at 8 pixels/update. Releasing vertical input damps velocity. Jump detaches; lateral input can change side or detach; losing rope can detach. These values explain traces, not a replacement motion solver. R3 (`Player.Update`: `SetControls` call `IL_1010`, `FindPulley` call `IL_33B5`, `PostUpdate` call `IL_860F`).
